## BUG-01 — session destroyed by `bookable_slots` (P1)

`backend/clinic_core/api/v1/slots.py` — `_elevated()`

### What was wrong

`_elevated()` ran one Marley read as Administrator (a Guest cannot read
Practitioner Schedule) and restored the caller with `frappe.set_user(original)`.
But `set_user()` does more than set a name — at `frappe/__init__.py:382-395` it
also resets `session.sid` to the username and **clears `session.data`**.

Restoring the name left the session payload emptied. Frappe wrote that emptied
session back, could not resolve the user on the next request, and returned a bare
`403 "No App"` for **everything** — reads included — until re-login.

### Root cause, narrowed by experiment

Not guessed. Each restore line was reverted independently against a live session:

| State | `auth.me` after `bookable_slots` |
|---|---|
| Both restores present | **200** ✅ |
| `session.sid` restore removed | **200** — still fine |
| `session.data` restore removed | **403** ❌ |
| Original code (neither) | **403** ❌ |

So **`session.data` is the load-bearing fix.** `sid` is restored as well because
`set_user()` corrupts it too and leaving a username where a token belongs is a
trap, but it is not what caused the outage. The code comment says exactly this —
an earlier draft of it blamed `sid`, which the experiment disproved.

### The fix

Snapshot `session.user`, `session.sid` and `session.data` before elevating, and
put all three back in the `finally` — after `set_user(original_user)`, since that
call resets them again.

### Verified

- `auth.me`, `list_patients` after `bookable_slots` → 200 (were 403)
- Full mobile sequence slots → **create** → 200
- Full mobile sequence slots → **reschedule** → 200
- All three staff roles survive it
- Guest booking unaffected (it never had a session to lose)

## BUG-02 — search `total` ignored the filter (P2)

`backend/clinic_core/api/v1/patients.py` — `list_patients()`

`frappe.db.count("Patient", filters)` accepts `filters` but **not** `or_filters`,
which is where the search terms live. A search matching 2 patients reported the
full active-patient count.

Two real consequences in the app, both confirmed:
- `patients.tsx:71` renders `"{total} registered"` → showed *"12 registered"* on a
  search returning 0 rows.
- `patients.tsx:47` decides pagination with `loaded < total` → the list requested a
  page that could only come back empty.

**Fix:** count through `frappe.get_list(..., fields=[{"COUNT": "*"}])`, which does
honour `or_filters`. (`fields=["count(name) as total"]` is rejected by this Frappe
version — it requires the dict form.)

**Verified:** narrow search `total == len(items)`; no-match search `total == 0`;
unfiltered list still counts every active patient.

## BUG-03 — detail endpoints wider than their lists (P3)

The *list* endpoints scoped correctly but the *detail* endpoints did not, and IDs
are sequential (`HLC-APP-2026-000NN`, `ACC-SINV-2026-000NN`) so they are guessable.

**Appointments** (`appointments.py` — `get_appointment`): applied the same rule
`_scope_filters()` uses for the list — a pure Physician is confined to their own
calendar; Admin/Healthcare Administrator/Nursing User are not.

**Invoices** (`invoices.py` — `_assert_invoice_access`): `list_invoices` goes
through `frappe.get_list`, which enforces Sales Invoice doctype permissions (hence
the doctor's correct 403). `get_invoice` used `frappe.get_doc`, which does not.
Added an explicit `frappe.has_permission("Sales Invoice", "read")` check to the
shared guard, and routed `get_invoice` through it so every invoice read — detail,
PDF and email — applies one rule.

**Verified:** doc2 → doc1's appointment **403**; doc1 → own **200**; admin and
reception **200**; doctor → invoice detail and PDF **403**; reception → both **200**;
guest **403** on everything.

## BUG-04 — reception schedule authority (policy)

Changed to the decision you made: **reception keeps the diary, not the contract.**

Split one permission into two:

| | `_assert_may_manage` (diary) | `_assert_may_set_hours` (weekly hours) |
|---|---|---|
| Covers | `block_time`, `set_leave`, `clear_unavailability` | `set_schedule` |
| Admin | ✅ | ✅ |
| Reception | ✅ | **⛔ 403** |
| Doctor (own) | ✅ | ✅ |
| Doctor (other) | ⛔ | ⛔ |

`practitioners.availability` now returns **two** flags — `can_manage` and the new
`can_set_hours` — because the mobile screen gated every affordance on one flag and
would otherwise offer reception an hours editor whose save could only 403.

Mobile changes (`app/(app)/availability/index.tsx`, `src/types/domain.ts`): the
per-day edit rows and the empty state now gate on `can_set_hours`; the "Add leave
or block time" button and the time-off list stay on `can_manage`. The explanatory
footer distinguishes the two cases.

**Verified:** reception `can_manage:true` / `can_set_hours:false`, `set_schedule`
**403**, `block_time` and `set_leave` still **200**.

## Regression tests — `backend/clinic_core/tests/test_qa_regressions.py`

16 new tests, one class per bug.

**These were themselves tested.** The first draft of the BUG-01 tests asserted on
`session.user`/`session.sid` and **passed even with the fix reverted** — worthless.
In-process, `set_user()` already sets `sid` to the username, so both look unchanged
either way. The tests now plant a marker in `session.data` and assert it survives,
which does catch it:

| | Result |
|---|---|
| With the fix | **16 passed** |
| Fix reverted | **4 failed** — with the diagnostic message naming BUG-01 |

Two further traps avoided, both from `[[clinic-test-data-traps]]`:

- `test_the_full_mobile_booking_sequence_works` scans forward for a working day
  instead of using today. Run after the working day ends, today has no free slots
  and the test would **skip** — silently not covering the P1 it exists for.
- The BUG-04 class never calls `set_schedule` *successfully*. It rewrites a shared
  Practitioner Schedule and cannot be rolled back; that is how an earlier run wiped
  Wed–Fri from the seed data. Only refusals and read-only flags are asserted.

## Deployment note

The bench (`~/projects/.../apps/clinic_core`) is a **copy**, not a symlink to the
Windows repo, so edits must be copied over. `cp` across the `/mnt/c` 9P mount
silently **dropped a byte per file** during this session (`practitioner` →
`practitione`, `customer` → `custome`), producing a `NameError` at runtime.
`cat <src> | sed 's/\r$//' > <dst>` transfers correctly. Always `diff` the bench
copy against the repo after deploying.
